# Фикс корня оверлапов word-границ в split-mode `find_candidates`

**Дата:** 2026-04-28
**Статус:** дизайн, готов к плану

## Задача

После snap-фикса (`docs/plans/2026-04-28-snap-overlap-fix-design.md`) часть оверлапов осталась — те, что приходят из `verified.json` уже пересекающимися. Memory `project_verified_json_overlap_fix.md` фиксировала это как открытую задачу.

Регрессия на `projects/2026-03-thermobags` показала 3 живых кейса (rows 51, 81, 90), все одинаковые по природе:
- Соседние предложения одной row матчатся в одном файле
- Их word-ренжи в транскрипте перекрываются на 1 граничное слово (whisper выдаёт ровно один токен между фразами — мисхиар или короткий филлер, которого нет ни в одном предложении сценария)
- Финальный CSV получает оверлап 0.08–0.16с — на таймлайне ~100мс аудио играет дважды

## Корневая причина

В split-mode `find_quote_parts` каждое предложение ищется через `find_candidates` независимо. `find_candidates` (`_scripts/match_timecodes.py:442–477`) находит n-gram-anchor (3–6 слов) в транскрипте и **расширяет ренж по длине предложения**:

```python
start_widx = max(0, widx - i)
end_widx = min(len(words) - 1, start_widx + len(pwords) - 1)
```

Расширение слепое: не знает, что соседнее предложение могло уже занять граничные слова. Когда whisper-транскрипт по словам не идентичен сценарию (быстрая речь, мисхиары), две независимые «расширенные» границы накладываются на одно и то же слово K в транскрипте — и оба кандидата захватывают K.

Whole-mode (`fuzzy_whole_match`) корректен по построению — `_lcs_align` + `_split_false_starts` дают непересекающиеся ренжи. Баг только в split-mode.

## Решение

После сбора пер-предложенческих кандидатов в `find_quote_parts` — пост-обработка `_dedupe_split_overlaps(parts_out, transcripts)`. Для каждой пары соседних script-частей, для каждой пары их кандидатов в одном файле с пересекающимися word-индексами:

```python
mid = (cb["words_start"] + ca["words_end"]) // 2
ca["words_end"] = min(ca["words_end"], mid - 1)
cb["words_start"] = max(cb["words_start"], mid + 1)
ca["end"] = round(words[ca["words_end"]].end, 2)
cb["start"] = round(words[cb["words_start"]].start, 2)
```

Граничное слово K при 1-word оверлапе (типичный кейс) уходит из обоих ренжей. При 2+-word оверлапе — режется по середине пересечения. Монотонное `min`/`max` обеспечивает безопасность при множественных кандидатах в одной части.

### Изменения в `find_candidates`

Не меняется. Уже возвращает `words_start`/`words_end` в каждом кандидате.

### Изменения в `find_quote_parts`

1. При сборке `parts_out` пробрасывать `words_start`/`words_end` в кандидаты (сейчас срезаются — строки 388–393 и 408–414):

```python
"candidates": [
    {"file": c["file"], "start": c["start"], "end": c["end"],
     "words_start": c["words_start"], "words_end": c["words_end"]}
    for c in cands
],
```

2. После цикла по предложениям, до финального `return`, вызвать `_dedupe_split_overlaps(parts_out, transcripts)`. Вызывается только в split-ветке; whole-mode не трогается.

3. `merge_adjacent_parts` (склейка single-cand соседей с gap < 3с) выполняется ДО `_dedupe_split_overlaps` — после клипа граничного слова разрыв может стать чуть больше 0с, но ≪ 3с, и склейка остаётся валидной. Порядок: клип → merge. Иначе можем подрезать слово, которое потом всё равно склеится в одну часть.

   **Корректировка:** ставим `_dedupe_split_overlaps` ПЕРЕД `merge_adjacent_parts`. После дедупа merge всё равно склеит, если в источнике соседи; если merge склеит обе части — они становятся одним кандидатом, оверлапа уже нет.

### `words_start`/`words_end` в выходном `candidates.json`

Оставляем — пригодится для будущей диагностики, не ломает контракт скилла `/match-timecodes` (агент игнорит лишние поля). Размер JSON растёт незначительно.

## Edge cases

**E1. Цепочка N>2 пересечений.** Попарный проход в порядке (i, i+1) обрабатывает последовательно; in-place изменения parts[i+1].words_start учтутся при проверке (i+1, i+2). Реальные цепочки короткие (1-2 пересечения на row).

**E2. Несколько кандидатов в части.** Cartesian product `ca × cb` для соседних частей. Если `ca` пересекается одновременно с `cb1` и `cb2` — монотонный `min(ca.words_end, mid - 1)` накапливает самый короткий клип. То же для `cb.words_start` через `max`.

**E3. Out-of-order по источнику.** Если `cb.words_start < ca.words_start` (нелинейная цитата: row собрана из позиций 41 → 06 → 38) — наш фильтр `ca.words_end < cb.words_start` срабатывает «как пересечение», но `mid` оказывается не там. Защита: `if cb["words_start"] < ca["words_start"]: continue` — обрабатываем только source-chronological пересечения.

**E4. Защита от схлопывания.** Если клип делает ренж невалидным (`new_a_end < ca["words_start"]` или `new_b_start > cb["words_end"]`), пропускаем эту пару. Кандидат остаётся пересекающимся; редкий случай, лучше чем выдать невалидный ренж.

**E5. Whole-mode.** `fuzzy_whole_match` уже даёт непересекающиеся ренжи. Гейт: `_dedupe_split_overlaps` вызывается только в split-ветке `find_quote_parts`.

**E6. Legacy-кандидаты без word-индексов.** Дешёвая защита: `if "words_start" not in cb or "words_end" not in ca: continue`.

## Что НЕ делаем

- **Не правим `find_candidates`.** Замена слепого расширения на per-sentence LCS — оверкилл для 3 кейсов. Поверхностный риск регресса (медленнее, может находить меньше вариантов на низком score).
- **Не понижаем порог whole-match.** Альтернатива «второй проход с min_score=0.7» меняет поведение поиска для всех случаев, не только с оверлапом.
- **Не валидируем у агента.** Агент работает с тем, что дал search; чинить причину дальше по цепочке — симптоматика.
- **Не лезем в snap.** Snap-фикс (`0906224` + `965308b` + `180ba24`) уже корректен; его контракт `min_start`/`max_end` не меняется. После корневого фикса warning о пересекающихся word-границах в `cmd_snap` (если бы он был) больше не актуален.
- **Не трогаем overlap между rows / между файлами.** Между rows клипы стоят последовательно на таймлайне (нет оверлапа в принципе). Между файлами — соседи не считаются соседями (см. snap-fix).

## Дополнение (2026-04-29): второй корень в `_safe_time`

### Что обнаружено

Регрессия Task 4 на термосумках показала, что `_dedupe_split_overlaps` чинит 5 из 6 кейсов. Row 81 остаётся с оверлапом 0.16с, причина — глубже:

- Слова 1003 ("Burger") и 1004 ("King.") в whisperx-транскрипте имеют `start=0, end=0` (тайм не выставлен)
- Cand A (предложение S1) кончается на word_end=1004; cand B (S2) начинается на word_start=1005
- **Word-индексы НЕ пересекаются** (1004 < 1005) — `_dedupe_split_overlaps` корректно пропускает пару
- Но `_safe_time(words[1004], "end", ...)` падает в fallback (val=0): идёт вперёд, находит `words[1005].end = 675.27` (валидный) → возвращает его
- Симметрично, `_safe_time(words[1005], "start", ...)` возвращает `words[1005].start = 675.11`
- Результат: cand A.end = 675.27 и cand B.start = 675.11 — оба тайма пришли из соседа cand B's first word, времена пересеклись

### Корневая причина

`_safe_time` (`_scripts/match_timecodes.py:80-102`) при fallback ищет соседа с **тем же** полем (`end` для `end`-lookup, `start` для `start`-lookup):

```python
direction = -1 if field == "start" else 1
for offset in range(1, 20):
    ni = idx + direction * offset
    if 0 <= ni < len(words):
        nval = words[ni].get(field, 0.0)  # ← то же поле
        if nval and nval > 0.0:
            return nval
```

Это семантически некорректно. `end[K]` — конец слова K, а `end[K+1]` — конец другого слова. Использовать `end[K+1]` как замену для `end[K]` означает приписать слову K длительность другого слова, перешагнув через всё, что между ними.

Whisperx-слова **не пересекаются по времени** (мы это проверили на baseline). Поэтому для слова K без валидного `end`:
- Истинный `end[K]` лежит между `words[K].start` (если валидный) и `words[K+1].start` (старт следующего слова)
- Использовать `words[K+1].start` как fallback для `end[K]` — корректная верхняя граница

Симметрично для `start`: использовать `end` предыдущего слова как нижнюю границу.

### Решение

В `_safe_time` при fallback искать **противоположное** поле:

```python
fallback_field = "start" if field == "end" else "end"
direction = -1 if field == "start" else 1
for offset in range(1, 20):
    ni = idx + direction * offset
    if 0 <= ni < len(words):
        nval = words[ni].get(fallback_field, 0.0)
        if nval and nval > 0.0:
            return nval
return 0.0
```

Это конструктивно: `end[K]` ≤ `start[K+1]`, поэтому возврат `start[K+1]` — безопасная (немного консервативная) оценка для `end[K]`. Симметрично для `start`.

### Edge cases

**E7. Цепочка пустых слов на границе.** Если слова K, K+1, K+2 все имеют пустые таймы, fallback пройдёт до K+3 (или дальше) и возьмёт его `start`. Это всё равно валидная верхняя граница для `end[K]`, просто свободнее.

**E8. Полностью пустой транскрипт хвост.** Если до конца `words[]` нет валидного `start`, возвращаем 0.0 (как сейчас). Дальше — ответственность вызывающего кода.

**E9. Все остальные call sites `_safe_time`.** Используется в `fuzzy_whole_match` и `find_candidates` — фикс там даёт более точные таймы, не вносит регрессии (раньше возвращалось «неправильное», теперь — «правильное и более тесное»).

### Тестирование

Smoke-тест добавляется в существующий `_dedupe_split_overlaps`-test (case E7, E8): синтетический `words[]` с пустым словом на границе, проверка что `_safe_time` возвращает корректную верхнюю/нижнюю границу.

Регрессия на термосумках — после фикса оверлапов в `candidates.json` должно быть **0** (было 6 до фикса, 1 после `_dedupe_split_overlaps` без фикса `_safe_time`).

### Что НЕ делаем

- Не меняем `MAX_WORD_DURATION` логику и не трогаем валидный-`end`-too-far-from-`start` clamp (lines 89-92) — это отдельный артефакт whisper, корректно обработан.
- Не убираем лимит 20 шагов поиска соседа — нет причин.
