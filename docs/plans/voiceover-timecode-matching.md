# Сопоставление таймкодов начитки со сценарием

## Контекст задачи

Слава записывает начитку (voiceover) для YouTube-ролика одним длинным видеофайлом (~20 минут). В записи есть:
- Чистовые реплики по сценарию
- Дубли (перезаписывал некоторые фрагменты по 2-3 раза)
- Оговорки, фальстарты
- Комментарии не по сценарию ("адский ветер", "сейчас ещё раз")
- Паузы между репликами

Сценарий хранится в `script.csv` — CSV с 4 колонками:
```
Слава | Таймкоды | Герой | Таймкоды
```

Задача: для каждой реплики Славы (колонка 1) найти точный таймкод в записи начитки и записать его в колонку 2.

## Что делали — пошагово

### Шаг 1. Транскрибация с word-level таймкодами

Запустили `transcribe.py` с флагом `--json`:
```bash
python _scripts/transcribe.py projects/tulips/raw/voiceover/1773574086.543356.mov --speakers 1 --json
```

Получили два файла:
- `transcript.txt` — человекочитаемый текст, один блок [00:02 → 18:51]
- `transcript.json` — JSON с пословными таймкодами (1897 слов), каждое слово имеет поля `word`, `start`, `end`

### Шаг 2. Попытка алгоритмического сопоставления (3 итерации)

Написали скрипт `match_timecodes.py`, который:
1. Читает `script.csv` и `transcript.json`
2. Нормализует текст (нижний регистр, убирает пунктуацию)
3. Ищет каждую реплику сценария в тексте транскрипта
4. При нескольких совпадениях (дублях) выбирает последний — он обычно чистовой

**Итерация 1 — LCS (longest common subsequence)**
- Скользящее окно по транскрипту, сравнение через LCS
- Результат: 41 из 74 реплик
- Проблема: слишком строгий порог совпадения, не учитывал ё/е

**Итерация 2 — LCS + нормализация ё→е**
- Добавили `text.replace('ё', 'е')` в нормализацию
- Снизили порог `min_match_ratio` с 0.6 до 0.45
- Результат: 48 из 74
- Проблема: LCS плохо работает с числами и перефразированием

**Итерация 3 — N-граммный поиск подстрок**
- Полностью переписали алгоритм
- Из реплики сценария генерируются n-граммы (от 6 до 3 слов)
- Каждая n-грамма ищется как подстрока в полном тексте транскрипта
- Через карту `char_to_word_idx` позиция символа переводится в индекс слова → таймкод
- Результат: **74 из 74 реплик найдены**
- Проблема: у некоторых слов таймкоды `start: 0, end: 0` (числа "100", "300", "60%"), что давало `??:??`

### Шаг 3. Агентный подход (финальный)

Алгоритмический подход нашёл все 74 реплики, но часть таймкодов были неточными из-за особенностей whisper. Перешли на ручное сопоставление через параллельных агентов.

**Подготовка:**
JSON-транскрипт весит ~70K токенов — слишком много для одного контекста. Создали компактный формат `words_compact.txt`:
```
   0 [00:02-00:03] Сегодня
   1 [00:03-00:03] вещаю
   2 [00:03-00:03] из
   3 [00:03-00:05] Кремля,
```
Одна строка на слово: индекс, таймкод [start-end], слово. 1897 строк.

**Исполнение:**
Запустили 4 параллельных Explore-агента, каждый получил:
- Свой кусок сценария (строки 1-40, 41-80, 81-120, 121-143)
- Полный `words_compact.txt`
- Инструкцию: для каждой реплики Славы найти соответствующий фрагмент в транскрипте, определить start первого слова и end последнего слова, при дублях выбрать последний

Агенты вернули таймкоды для всех 74 реплик. Результат — **значительно точнее** алгоритмического: нет `??:??`, лучший выбор дублей, учёт контекста.

### Шаг 4. Коррекция раздутых end-таймкодов

После ручной проверки обнаружили проблему: whisper растягивает `end` последнего слова перед паузой. Например, слово "сезон." имело `start: 113.8`, `end: 123.4` — на 9.6 секунд длиннее реального.

**Причина:** WhisperX присваивает `end` последнего слова до паузы = `start` следующего слова после паузы. Получается, что одно слово "длится" всю паузу.

**Фикс:**
- Нашли все слова в транскрипте, где `end - start > 1.5 сек` (53 таких слова из 1897)
- Для каждой из 74 реплик проверили: если end-таймкод попадает на раздутое слово, заменили на `word.start + 1 сек`
- Исправлено **9 таймкодов**, самая большая коррекция: 02:03 → 01:55

## Результат

`script.csv` содержит точные таймкоды для всех 74 реплик Славы в формате `MM:SS -> MM:SS`.

## Важные нюансы для скилла

### Особенности транскрипции (WhisperX)
- Числа ("100", "60%") иногда получают таймкоды `0, 0` — нужно использовать соседние слова
- Последнее слово перед паузой: `end` раздувается до начала следующего слова. Фикс: если `end - start > 1.5s`, то `end = start + 1s`
- Буква ё в транскрипте может быть и ё и е — нормализовать при сравнении

### Особенности начитки
- Слава записывает одним файлом, есть дубли → при нескольких совпадениях выбирать последний (самый поздний)
- Есть комментарии-мусор ("адский ветер", "сейчас ещё раз") — игнорировать
- Есть фальстарты (начал фразу и бросил) — не путать с полными репликами

### Алгоритм vs агенты
- **N-граммный алгоритм** нашёл все 74 реплики, но часть таймкодов кривые (из-за whisper-артефактов). Хорош для первого прохода.
- **Агенты с word_compact.txt** дали точнее результат, потому что видят контекст и могут выбирать соседние слова когда нужно. Хороши для финальной вычитки.
- **Оптимальный подход:** алгоритм для первого прохода + агентная проверка проблемных мест.

### Формат CSV сценария
- Колонка 1 (Слава): текст реплики. Пустые строки и строки "ЭПИЗОД ..." — пропускать
- Колонка 2 (Таймкоды): формат `MM:SS -> MM:SS`
- Колонки 3-4 (Герой): реплики и таймкоды героя из других источников (созвоны), заполняются отдельно

### Файлы проекта
```
projects/{name}/
  raw/voiceover/          ← исходное видео начитки
  transcripts/            ← .transcript.json (word-level) + .transcript.txt + words_compact.txt
  script/                 ← script.csv (сценарий с таймкодами)
  script/match_timecodes.py ← скрипт алгоритмического сопоставления (опционально)
```
